# 新聞工作流程的一般設計建議

以下是概念設計，不是現有系統的節點清單或部署描述。

## 來源與去重

收集候選來源後，擷取足以核對事實的全文，保留原始發布時間與來源連結。讀取歷史紀錄，先比較正規化來源 URL，再檢查標題、內容與事件是否重複。

檔名、顯示標題與文章身份應分開。檔名可以供人辨識，內部穩定識別值用於防止重試造成重刊；不同來源同一事件仍需額外判斷，不能只靠一個 hash。

## 文章生成與審查

文章以讀者需要知道的具體進展開頭，將事實、必要背景與白話解釋自然整合。避免機械式固定大標、硬造案例或重複結論。若使用假設例子，在句中明確標示。

將來源支持的事實與編輯分析分開辨識，但不必用醒目的制式大標。保留數字單位、歸因、時點、條件、否定和計畫／成果差異。

形式驗證與語義審查分開：JSON 結構、必填欄位和精確引文可由程式檢查，但引用存在不代表推論正確。實質修訂後重新獨立審查；保留原始失敗，不修改分數或證據假裝通過。

## 圖片與網站呈現

圖片驗證應涵蓋內容相關性、尺寸、格式、實際可讀性、重複、授權與署名。遵循圖片供應商規範與使用者授權；為搜尋和重試設定明確上限。

內文圖片與首頁縮圖通常是不同欄位或主題介面，不能只驗證文章內頁。測試首頁、分類頁、手機版和其他文章卡片區域。

文章 taxonomy、主要分類、麵包屑和結構化資料可能由不同元件產生，應分別讀回核對。URL slug 不應被當成分類正確性的證據。

## 發布與讀回

正式寫入前先以穩定身份查詢是否已存在。只有全部必要檢查通過且得到適當授權才發布。保留發文回應，接著核對公開可讀頁面、內容、分類、圖片與必要 metadata。

寫入回應遺失或逾時時先查詢結果，不直接重發。只有確定未寫入，才考慮安全重試。

## 歷史與交易

使用同一協調機制管理所有會發布或更新歷史的入口。採用明確的執行身份、目前資料版本與收據紀錄，避免平行執行產生重複。

修改歷史檔前檢查新鮮版本，完整備份並讀回。追加後精確核對原有值未改變與新增值正確，再提交成功狀態。不要用有損解析值重建原始資料。

一般檔案寫入不應直接宣稱具備原子交易保證。中斷後留下明確待恢復狀態，依證據判斷，不自動偷鎖或重寫。
